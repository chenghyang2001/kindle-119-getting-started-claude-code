# PROMPTS：第 3 章「提問的藝術」自己改寫的例子

## 例 1：Context＋Goal＋Constraints

書上的重點：不要只丟一句「幫我重構」，要交代**背景（Context）**、**想要的結果（Goal）**、**不能做的事（Constraints）**。

### ❌ 原本會寫的模糊版

```text
幫我重構 processOrder，它太亂了。
```

### ✅ 改寫版

```text
Context：
src/processOrder.ts 是下單流程，巢狀 6 層 if/else，驗證與寫 db 混在一起。
tests/processOrder.test.ts 有 7 個測試在保護目前行為。

Goal：
只重構「驗證」這一段：每個檢查抽成具名函式，processOrder 改成 early return。
重構後讀 processOrder 的人，三行內就能看出「先驗證、後寫入」。

Constraints：
- 不准改回傳格式 { ok, orderId?, error? }，錯誤訊息文字一字不改。
- 不准碰 db 寫入那一段（下一步才處理交易）。
- 不准新增套件。
- 改完跑 npm test，全部通過才算完成；不通過就停下來告訴我哪裡不通過。
```

**為什麼比較好**：Claude 不用猜「亂」指的是什麼、能改到哪裡；
「錯誤訊息一字不改」「不准碰 db」這兩條把範圍鎖死，避免一次改太多。

## 例 2：先要計畫再動手

書上的重點：大一點的改動，先叫 Claude 產出計畫、你確認後才寫程式，
避免它一路改下去才發現方向錯。

### ❌ 直接動手版

```text
把 processOrder 的兩個 db 寫入改成交易。
```

### ✅ 改寫版

```text
我想把 processOrder 裡的 insertOrder 和 decrementStock 包進同一個交易。
先不要改任何程式碼。請先寫一份 PLAN.md，內容包含：
1. 要改哪些檔案、每個檔案改什麼（條列，不要貼程式碼）
2. Db 介面要怎麼擴充才能支援交易，假 db 要怎麼模擬回滾
3. 要新增哪個測試來證明「寫入失敗會回滾」
4. 你看到的風險（例如錯誤被吞掉、既有測試要不要改）
寫完停下來等我看，我說「照計畫做」你才開始改程式。
```

**為什麼比較好**：計畫階段便宜、改程式階段貴。
在 PLAN.md 就能發現像「驗證順序改變會讓錯誤訊息不同」這種問題（本次演練真的在計畫裡抓到了）。
